# Implementation Plan: autopsy-sources

## Overview

Implements `.kiro/specs/autopsy-sources/requirements.md` per `.kiro/specs/autopsy-sources/design.md`: source clients that turn `(purl, as_of)` into `Signals` plus evidence for npm and PyPI. The pure half (URL builders, parsers, `has_fix`, repo resolution, assembly, Resting predicate) goes in `backend/core/sources/`; the I/O half (gateway, limiter, cache, clients, session, `autopsy_async` / `autopsy`) goes in a new `backend/sources/` package. Each implementation task includes its own example tests and property tests as sub-tasks. T0 is scaffolding, so it carries guard tests instead of properties. T12 is a **manual** task that the maintainer runs; the tasks after it depend on its output.

```mermaid
graph LR
  T0 --> T1 --> T2 --> T3 --> T4 --> T5 --> T6 --> T7 --> T8 --> T9 --> T10 --> T11 --> T12 --> T13 --> T14
```

T2–T5 depend only on T0 and T1, and T7 only on T1; the chain is kept linear so each task starts from a green suite. T13 is blocked until the maintainer has committed the cassette in T12.

## Notes

- Each implementation task includes its own unit and property tests as sub-tasks; tests land immediately after the code they exercise. Tests against **recorded** bodies (T13) wait for the manual recording (T12), so T2–T10 use hand-built documents in the shapes recorded in design §6.
- Pure-half code and tests are under `backend/core/sources/`; I/O-half code and tests under `backend/sources/`. Pure tests resolve fixtures via `Path(__file__)`; I/O tests reach the cassette at `Path(__file__).parents[2] / "core" / "sources" / "tests" / "fixtures" / "recorded"`.
- Run every Python tool from `backend/` via `uv run`. Never call `pytest`, `ruff` or `mypy` bare. Property tests use `HYPOTHESIS_PROFILE=ci` for the gate.
- No test uses the network. The only network tasks are T0.1 (`uv add`) and T12 (manual). No task installs or runs any package under analysis.
- Do not add `pytest-asyncio` or `respx`. Async code is driven by `asyncio.run` in synchronous tests; HTTP is faked with `httpx.MockTransport` (D13).
- The GitHub token is only ever an argument. Neither package reads the environment; only `scripts/record_source_responses.py` does.
- If a property fails, fix the code, or the oracle when the oracle is wrong, and record the counterexample in `docs/KIRO_JOURNAL.md`.
- Before each task, read the SRC-* requirement IDs it names in `requirements.md`; requirements win over the design if they differ. Read `.kiro/specs/autopsy-sources/requirements.md` D1–D16 once at the start.
- Already done while writing this spec: `.kiro/steering/structure.md` now describes `backend/core/sources/` (pure half) and `backend/sources/` (I/O half) and their import rules.
- If a recording changes an MM-ANC expectation (T12.3), the expectation is not edited as part of this spec.
- Review decisions applied after T10 (journal entry of 10 Nov): `backend/sources` may import `core.scoring.types` and nothing else from `core.scoring` (SRC-DEP-4); a non-string OSV `next_page_token` fails the chunk (design §6.1); `Limits.github_rate_floor >= 1` (SRC-GH-6); `osv_vuln_url` rejects `.` and `..`; an unusable OSV `vulns` entry fails that package's S7 (SRC-OSV-3); GitHub fields follow SRC-GH-9 (absent/null is an absence, wrong-typed is `UNEXPECTED_SHAPE`, one malformed commit node makes S5 unknown); `user:password@` is stripped from every stored URL (SRC-SEC-3); the `osv.vuln` cache subject is `<id>#<ecosystem>/<name>` (design §5).
